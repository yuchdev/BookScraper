# Dependency Audit - cryptography addition - 2026-09-30

**Scope:** Direct and transitive dependencies introduced by the `cryptography>=50.0.1` addition
(roadmap milestone 0001 / task 02.1 / 06 — certificate expiry inspection: parses the first
CERTIFICATE block of the X.509 client PEM; threat-model requirements ROT-4/ROT-5 in
`docs/security/2026-09-30-x509-certificate-rotation.md`). Audit covers `pyproject.toml`,
`uv.lock`, and the resolved environment under `.venv/`.
Tool: `uvx pip-audit` against the uv-managed virtual environment.

## Findings

| Severity | Finding                                                                                      | Evidence                                                                       |
|----------|----------------------------------------------------------------------------------------------|--------------------------------------------------------------------------------|
| INFO     | No known CVEs in any installed package                                                       | `uvx pip-audit` — "No known vulnerabilities found"                             |
| INFO     | `cryptography` 50.0.1 — Apache-2.0 OR BSD-3-Clause — runtime, ships in wheel               | `pyproject.toml` `[project] dependencies`; dual-license, both permissive → Allow |
| INFO     | `cffi` 2.1.1 (transitive via cryptography) — MIT-0 — runtime                               | `uv.lock` transitive dep of `cryptography`; MIT-0 → Allow (see note)          |
| INFO     | `pycparser` 3.0 (transitive via cffi) — BSD-3-Clause — runtime                             | `uv.lock` transitive dep of `cffi`; BSD-3-Clause → Allow                      |

**Note on cffi MIT-0:** MIT-0 is an OSI-approved variant of MIT that removes the attribution
clause, making it strictly more permissive than the already-allowed MIT. It does not appear in
the policy's explicit Allow list; it is ruled Allow here on that basis. The policy's Allow list
has been updated to include MIT-0 explicitly (see `.claude/skills/dep-audit/references/license-policy.md`).

**Note on cryptography runtime status:** unlike the `mongomock` packages audited on 2026-09-29,
`cryptography` is a **runtime** dependency that ships in the wheel. It contains compiled
Rust/OpenSSL extension code. This makes it a security-critical parsing surface for key material
(PEM certificate blocks) and warrants routine patch-level monitoring — patch promptly when a
security advisory is issued.

## Verdict

No CRITICAL or HIGH findings. The `cryptography` package and its two transitives carry only
permissive licenses (Apache-2.0 OR BSD-3-Clause, MIT-0, BSD-3-Clause) and present no
copyleft or license-compatibility risk to the distribution model. No CVEs were found in any
installed package at the time of this audit. The compiled-code nature of `cryptography`
makes it higher-priority for patch updates than a pure-Python dependency, but there is no
present blocker.

Do not block merge on this audit.

## Recommended actions

1. Add `cryptography` to the project's routine dependency-update cadence and patch promptly
   on any security advisory — it is the parsing surface for X.509 key material.
2. Add MIT-0 to the Allow tier of the license policy (done in this audit cycle — see
   `.claude/skills/dep-audit/references/license-policy.md`).
3. Re-run `uvx pip-audit` after any future bump of `cryptography`, `cffi`, or `pycparser`
   to confirm no new advisories are introduced.
